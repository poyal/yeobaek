# 뷰어 E2E와 검증 기준

아래 항목은 제품의 **검증 요구**이며 일괄 통과 기록이 아닙니다. 실행한 항목·실패 수정·미실행 사유는 해당 버전의 `docs/releases/v<버전>/AGENTS.md`에 남깁니다.

## 1. 검증의 구분

| 종류 | 확인할 내용 | 이 검사로 대신할 수 없는 것 |
| --- | --- | --- |
| 순수 Kotlin 단위 검사 | 디코딩, 줄바꿈, 인덱스, 검색, 오프셋 불변식 | Android 실제 글꼴과 스크롤 성능 |
| Android 저장소 검사 | Room 이전, 폴더 권한·캐시 확정·복구, SAF 계약 | 공급자마다 다른 실제 폴더 선택 UI |
| Compose UI 검사 | 메뉴·설정·책갈피·검색·화면 재생성 | 실제 프로세스 사망, 고주사율 프레임 품질 |
| 호스트/시스템 검사 | 폴더 선택기·재부팅, 앱 재시작, 실제 PID 교체, 덮어 설치 | 제조사별 실물 기기의 성능 |
| Macrobenchmark·트레이스 | 본문 표시 시간, 프레임 분포, 병목 | 글자 누락·순서 오류와 사용자 체감 전체 |
| 실제 읽기 점검 | 블록 경계, 글꼴, 조작감, 긴 독서 | 실행하지 않은 OS와 파일 형식 |

검사 결과 판정·전용 에뮬레이터 보호·실제 PID 확인 절차는 [Android 개발 기준](development.md)과 [릴리즈 운영](release.md)을 따릅니다. 다른 앱의 과거 통과 수치를 여백의 결과로 사용하지 않습니다.

## 2. 테스트 자료

외부 소설을 수집하지 않고 합성 본문 또는 사용 허용이 확인된 자료로 검사합니다. 각 fixture에 생성 seed, 문자 수, 원본 바이트 수, charset, SHA-256, 예상 결과를 기록합니다.

| ID | 자료 | 확인 목적 |
| --- | --- | --- |
| T01 | UTF-8, BOM 유무, 한글·숫자·영문 | 일반 열기와 표준 표시 |
| T02 | CP949 확장 한글, EUC-KR 범위 문자 | 별칭·인코딩 판정·수동 변경 |
| T03 | UTF-16 LE/BE, BOM 유무 | BOM·endianness·NUL 판정 |
| T04 | CRLF/LF/CR 혼합, 마지막 LF 유무 | 버퍼 경계 정규화와 공백 보존 |
| T05 | 이모지 ZWJ, surrogate pair, 분해 한글, 결합 악센트 | 표시 조각과 저장 블록의 경계 |
| T06 | 일반 문단의 1/10/50MiB | 지원 용량의 성능·정확성 |
| T07 | 100MiB 및 안전 한도 초과 스트림 | 상한 준수, 종료·정리, OOM 방지 |
| T08 | 줄바꿈 없는 1MiB 한 문단, 긴 URL·공백 없는 단어 | 거대한 Text 항목 방지·분할 정확성 |
| T09 | 한 글자 줄·빈 줄 수십만 개, 긴 공백·탭 | 인덱스 객체 폭증·빈 줄 높이 |
| T10 | 처음은 UTF-8처럼 보이고 뒤에서 오류가 나는 파일 | 표본 오판·전체 검증 |
| T11 | 잘린 멀티바이트·불완전 UTF-16·바이너리를 .txt로 변경 | 명확한 실패와 원본 보존 |
| T12 | 같은 이름 다른 내용, 다른 이름 같은 내용 | 문서 정체성·내용 버전 분리 |
| T13 | 검색어가 모든 저장/화면 블록 경계에 걸린 본문 | 검색 누락·중복 방지 |
| T14 | 짧은 파일, 0바이트, BOM만 존재, 공백만 존재 | 빈 문서 정책과 0 나누기 방지 |
| T15 | 한글·영문·아랍어 혼합, 미지원 글리프 | 방향·글리프 문제를 인코딩 오류와 구분 |

T06뿐 아니라 T08·T09를 같은 성능 작업에서 검사합니다. 파일 용량이 작아도 문단 형태에 따라 더 어려울 수 있습니다.

## 3. 반드시 유지할 불변식

1. 정규 본문을 블록 순서대로 연결하면 정규화 규칙 v1의 결과와 정확히 같습니다.
2. 각 블록의 문자 범위는 누락·중복 없이 연속하며 UTF-8 경계가 유효합니다.
3. 같은 파일·인코딩·정규화 버전은 같은 `contentVersion`과 문자 좌표를 만듭니다.
4. 테마·글자 크기·회전은 본문 버전이나 책갈피 문자 오프셋을 바꾸지 않습니다.
5. 검색 결과 범위는 정규 본문에서 실제 질의와 일치합니다.
6. 폴더 연결·본문 준비의 실패·취소가 외부 원본이나 기존 위치를 바꾸지 않습니다.
7. 오래된 비동기 결과·저장 요청은 새로운 책·설정·세션을 덮지 않습니다.
8. 메모리·파일 핸들·작업 수에 상한이 있고 화면을 닫으면 작업이 정리됩니다.
9. 앱 설정·형식별 표시 옵션·책별 본문 정보가 독립적이며, 한 범위의 변경·초기화가 다른 범위를 덮지 않습니다.

작은 무작위 문자열과 여러 버퍼 크기로 경계 조건을 생성해 검사합니다. 실제 글꼴에 따른 경계 높이와 줄바꿈은 Android 기기 검사로 보완합니다.

## 4. 실제 사용 시나리오

EPUB 장별 탐색은 `EpubNavigationTest`와 `EpubReaderTest`에서 메뉴 숨김 후 아이콘 유지, 첫·마지막 장의 비활성화, 연속 탭 방지, 원문 뒤 장 끝 버튼, 짧은 장, 중첩 목차 강조, 긴 장의 위치·책갈피·글꼴 변경·재생성, 페이지 모드에서 돌아온 뒤 터치 스크롤을 검사합니다. `EpubJourneyTest`는 release에서 실제 스와이프로 장 끝 버튼에 도달하고, 큰 글씨의 장별 스크롤과 페이지 모드 각각의 실제 PID 교체 후 복원을 검사합니다. 재시작 후에는 설정 범위를 다시 **이 책**으로 선택해 기존 책별 값을 바꿉니다. 실행 여부와 결과는 버전별 기록에 구분해 남깁니다.

메뉴를 숨긴 본문의 고정 여백은 별도로 검사합니다. EPUB은 본문과 전체 읽기 영역의 크기 일치·메뉴 반복 전환 후 문장 좌표 보존을 확인합니다. `ReaderScrollTest`는 TXT 중간 위치의 위아래 텍스트 영역과 앵커를, `ReaderViewportTest`는 단색으로 채운 긴 PDF·PNG·CBZ에서 실제 뷰의 위·중간·아래 픽셀과 메뉴 전환 전후 위치를 확인합니다. 페이지 맞춤의 비율 여백을 스크롤 본문을 자르는 고정 영역으로 잘못 분류하지 않습니다.

설정 화면은 `SettingsLayoutTest`로 일반·TXT·PDF·EPUB·이미지·앱 정보·업데이트·빠른 설정의 스크롤 끝까지 확인하고 원본 화면을 남깁니다. EPUB 원본 서식 해제·페이지 모드, 이미지 좌우 넘김의 조건부 항목도 포함합니다. `SettingsChoicesTest`는 좁은 폭·글씨 200%에서 선택 항목의 균등 배치, 텍스트 잘림, 선택 전후 위치와 크기를 대조합니다. 기기 화면 폭과 시스템 글씨 배율을 바꿨으면 실행 결과를 따로 기록하고 검사 후 복구합니다.

| U31 | 이어 읽기 확인 중 연속 탭·회전·원본 이동·내용 변경 | 한 요청만 적용, 재연결·본문 이전 안내, 이전 기록 보존 |

프로세스 종료 검사는 별도 호스트 프로세스에서 진행합니다. 테스트 앱 내부의 Activity 재생성만으로 U07을 통과 처리하지 않습니다. 마지막 1초 내 미저장 위치와 이미 저장된 위치를 구분합니다.

시작 화면 판정과 후보 소비의 세부 조건은 [시작·이어 읽기 흐름](architecture.md)을 따릅니다.

현재 TXT·EPUB·PDF·이미지의 옵션을 서로 다르게 지정하고 형식 간 왕복·개별 초기화·업데이트 후 보존을 검사합니다. 과거 TXT 출시의 결과에는 당시 없던 뷰어의 검사를 포함하지 않습니다. [기능·설정 분리](architecture.md)

## 5. 성능 측정 조건

M0에서 기준 기기의 모델·RAM·SoC·OS·해상도·density·fontScale·주사율을 고정합니다. 최소 지원 OS, API 31 이상 프레임 분석 기기, 최신 안정 OS를 구분하고 에뮬레이터를 실기기 FPS의 근거로 사용하지 않습니다.

- release와 동일한 최적화 조건의 `non-debuggable/profileable` 빌드를 사용합니다.
- 소스 커밋, APK 해시, 빌드 변형, 컴파일 모드, Baseline Profile 적용 여부를 기록합니다.
- 충전·절전 모드·온도·백그라운드 작업을 통제하고 thermal throttling 여부를 남깁니다.
- 동일 fixture와 동일 손짓 시나리오로 최소 10회, 각 30초의 스크롤 구간을 측정합니다.
- 열기·설정 반영 등 지연 시간은 최소 30회 개별 표본에서 P50/P95를 계산합니다. 작은 표본의 P95가 불안정할 수 있음을 함께 기록합니다.
- 최초 본문 준비, 앱만 재시작한 열기, 정규 본문 캐시가 있는 열기, 캐시 재생성 열기를 분리합니다.
- 디스크 파일 페이지 캐시는 앱 종료만으로 비워지지 않습니다. 이를 완전한 cold I/O 측정이라고 부르지 않습니다.

### 측정값과 목표

| 항목 | 측정 정의 | 목표 제안 |
| --- | --- | --- |
| 스크롤 P95/P99 | 실제 스크롤 구간의 `frameOverrunMs` | 60Hz P95 ≤ 0ms, P99 ≤ 8ms |
| 기한 초과 비율 | 같은 구간에서 overrun > 0인 프레임 / 수집된 프레임 | ≤ 5% |
| 새 블록 진입 | 파일 처음이 아닌 미방문 영역의 스크롤 구간 | 위 목표 적용, 반복 blank flash 없음 |
| 재열기 | 파일 탭 또는 이어 읽기 확인 선택부터 원본 전체 해시 검증과 목표 문장 표시까지 | 로컬 10MiB·캐시 존재 P95 ≤ 2초, M0 확정 |
| 최초 준비 | 파일 탭부터 원본 확인·본문 준비·첫 프레임까지 | 1MiB 1초 / 10MiB 3초 / 50MiB 15초 이내 P95 |
| 폴더 조회 | 로컬 현재 폴더 1,000항목 조회·정렬·첫 표시 | P95 ≤ 1초, 전체 트리 스캔 없음 |
| 설정 변경 | 최종 입력 이벤트부터 같은 문장의 새 레이아웃 표시까지 | P95 ≤ 300ms |
| 메모리 | 빈 서재 기준과 열람 중 Java+native heap의 차이 | 50MiB 본문에서 증가 ≤ 64MiB 목표 |
| 장시간 안정성 | 동일 시나리오의 시작·중간·종료 메모리, FD, 작업 수 | 누적 증가 원인 없음, OOM 없음 |

`frameOverrunMs`는 API 31 이상에서 제공됩니다. 낮은 API는 프레임 추적과 CPU 시간 등 가능한 지표를 사용하고 동일한 overrun 값이 있다고 가정하지 않습니다. `FrameTimingMetric`과 앱 내부 JankStats의 휴리스틱 비율은 정의가 다르므로 같은 수치로 합치지 않습니다. [Macrobenchmark 측정값](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics), [JankStats](https://developer.android.com/topic/performance/jankstats)

120Hz는 실제 활성 주사율을 확인하고 별도 deadline 기준으로 분석합니다. 프레임 시간의 CPU 값만 보고 표시 기한 준수로 판정하지 않습니다. Baseline Profile은 동일한 비교 조건으로 효과를 측정하며 특정 개선 비율을 여백에 보장하지 않습니다. [Baseline Profiles](https://developer.android.com/topic/performance/baselineprofiles/overview)

외부 공급자의 다운로드 지연은 전체 사용자 대기 시간에도 남기되 원본 검증·디코딩·인덱싱 시간과 구분합니다. 첫 준비·재열기 목표는 로컬 공급자 조건이며, 사용자가 이어 읽기 확인에 응답하는 시간은 측정에서 제외합니다.

## 6. 결과를 남기는 방식

현재 `.tools/verification/`에 실행별 APK 해시·기기·instrumentation 결과·화면·성능 원시값을 저장합니다. 다음 구조는 향후 실물 기기 자료에도 적용합니다.

```text
.tools/verification/<run-id>/
  manifest.json       소스, APK 해시, 기기, fixture, 설정
  junit/              실제 테스트 결과
  benchmark/          원시 표본과 집계
  traces/             Perfetto 자료
  screenshots/        실패 및 경계 확인
  summary.json        PASS / FAIL / NOT_RUN, 미실행 이유
docs/releases/v<version>/AGENTS.md
                      공유할 결과 요약과 제한
```

명령 종료 코드 외에 예상 테스트 이름·실행된 이름·실패·중단·생략·누락을 대조합니다. 작업 중에는 새 실행 폴더로 실패 근거를 구분하고, 종료 후 최종 사실을 기록한 뒤 원본을 삭제합니다. 화면·APK가 바뀌면 이전 후보의 통과를 재사용하지 않습니다.

검사 규모는 변경에 맞춥니다. 문서 수정은 문서 확인, 디코더 변경은 관련 fixture, UI 변경은 관련 화면·성능 회귀를 우선합니다. 최종 후보에 필요한 전체 검증을 마치면 같은 후보를 이유 없이 반복 검사하지 않습니다.

## 7. 출시 판정

TXT 필수 기능·본문 불변식·데이터 보존·지원 용량의 측정 목표를 통과해야 합니다. 심각한 본문 누락·앵커 오류·인코딩 손실·ANR·OOM은 출시 차단 항목입니다. 미검증 제조사 기기와 공급자는 별도 제한으로 기록합니다.

공개 배포 시에는 검증한 APK의 바이트·앱 ID·버전·서명과 배포 파일을 대조합니다. 실제 빌드·검증·게시 상태는 버전별 검증 기록을 확인합니다.
