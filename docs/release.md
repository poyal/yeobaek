# 여백 검증·릴리즈 운영안

작성일: 2026-10-13. 빌드·개인 서명·전용 에뮬레이터 검증 스크립트와 GitHub 기반 앱 내 업데이트를 구현했습니다. 이 문서는 검증·배포의 운영 기준입니다. 공개 게시 자동화는 아직 없으며 실제 실행 기록은 [버전별 검증 기록](releases/v0.1.0/AGENTS.md)에 남깁니다.

## 1. 개발 중 검사와 출시 후보 검사

| 단계 | 할 일 |
| --- | --- |
| 개발 중 | 변경한 기능의 단위 검사·실패 재현·필요한 Lint를 먼저 수행합니다. |
| 성능 변경 | 해당 독서 시나리오와 동일 fixture로 프레임·메모리를 비교합니다. |
| 후보 확정 | 필요한 전체 검사를 수행하고 소스와 APK를 고정합니다. |
| 게시 | 검증한 산출물과 게시할 산출물이 같은지 확인합니다. |
| 문제 조사 | 로컬에서 좁혀 보고 원격 환경 문제가 있을 때만 추가 진단합니다. |

문서만 바꾼 작업 때문에 APK 재빌드나 전체 E2E를 반복하지 않습니다. 반대로 앱에 포함되는 도움말 자산·빌드·검사 코드가 바뀌면 영향을 평가합니다.

초기에는 무거운 Android 에뮬레이터 CI를 매 push·PR마다 실행하지 않는 안을 권장합니다. 빠른 정적 검사와 무거운 기기 검사를 구분하고, 원격 진단이 필요한 이유를 남깁니다.

## 2. 실행별 증거

검증마다 새 실행 ID와 결과 폴더를 만듭니다. 최소 기록은 다음과 같습니다.

```text
소스: 커밋, 미커밋 변경 여부, 의존성 조합
산출물: APK 경로, SHA-256, 바이트 수, 앱 ID, versionCode, versionName
기기: 모델/AVD, OS, ABI, 해상도, fontScale, 활성 주사율
검사: 이름, fixture 해시, 시작/종료, PASS/FAIL/NOT_RUN, 로그
범위: 에뮬레이터/실기기, debug/release, 누락 및 제외 이유
```

예상 테스트 이름과 실제 실행 이름을 대조합니다. 실패·오류·생략·누락·중단·보고서 부재를 통과 처리하지 않습니다. 프레임 성능은 원시 표본·측정 구간·빌드 조건을 함께 남깁니다.

이전 버전의 성공 표시는 새 버전 문서에 복사하지 않습니다. 과거 결과는 당시 APK와 환경의 증거입니다.

## 3. 최종 후보의 필수 확인

- TXT 디코딩·정규화·블록 경계·검색·앵커 불변식을 확인합니다.
- 기본/큰 글씨·밝게/어둡게·키보드·회전·좁은 창을 확인합니다.
- 실제 OS 폴더 선택기로 시작 위치 설정·취소·재부팅·권한 상실 복구를 확인합니다.
- Activity 재생성과 실제 프로세스 종료를 별도로 검사하고, 새 실행의 이어 읽기 확인과 폴더 보기 동작을 확인합니다.
- release 최적화 APK에서 서재·검색·설정·읽기 복원을 확인합니다.
- 앱 설정·TXT 표시 옵션·책별 인코딩의 독립성과 개별 초기화 범위를 확인합니다. 후속 뷰어가 추가되면 형식 간 왕복·설정 보존도 포함합니다.
- 지원 용량과 기준 기기의 스크롤 성능을 측정합니다.
- 직전 공개 버전이 있으면 삭제 없이 덮어 설치하고 데이터 보존을 검사합니다.

덮어 설치 비교에는 시작 폴더·영속 읽기 권한·독서 세션 후보, 외부 원본 해시, Book ID, 인코딩·본문 버전, 문자 앵커·책갈피·읽기 설정을 포함합니다. 캐시를 새로 만드는 것은 허용할 수 있지만 사용자 기록 손실과 구분합니다. 스키마 변경이 의도한 값만 바꾸는지 확인합니다.

## 4. 서명과 배포 파일

여백은 독립된 서명 키를 사용하고 첫 배포 이후 업데이트의 연속성을 유지합니다. 키·비밀번호·개인 SDK 설정·키 백업은 Git과 공개 산출물에 넣지 않습니다.

release 빌드 성공만으로 서명 완료를 판단하지 않습니다. 앱 ID·증가한 versionCode·예상 versionName·서명을 최종 APK에서 읽어 확인합니다. 직전 APK가 있다면 인증서와 기존 앱 덮어 설치를 검증합니다.

직접 APK를 배포하면 검증한 파일을 복사해 해시를 고정한 뒤 그대로 게시합니다. 게시 단계에서 새로 빌드한 다른 APK로 바꾸지 않습니다. Play를 선택하면 AAB·서명·테스트 트랙 등 채널에 맞는 별도 절차를 추가합니다.

## 5. 직접 APK 게시를 선택한 경우

앱 내 업데이트는 `poyal/yeobaek` 저장소의 최신 정식 GitHub Release를 읽습니다. 태그는 `v<major>.<minor>.<patch>`, 첨부 파일은 `yeobaek-<version>.apk`와 `yeobaek-<version>.sha256`이어야 합니다. draft·prerelease·업로드 미완료·공식 주소가 아닌 파일·GitHub SHA-256 digest가 없는 APK는 설치 후보로 쓰지 않습니다.

체크섬 파일에는 `64자리 SHA-256  yeobaek-<version>.apk` 한 줄만 넣습니다. 해당 해시가 GitHub asset digest와 같아야 합니다. 앱의 versionName은 태그에서 `v`를 뺀 값과 일치하고 versionCode는 이전 설치보다 높아야 합니다. 최초 배포 이후 같은 서명 키를 계속 사용합니다. 테스트 APK·서명 키·비밀번호는 첨부하지 않습니다. 스크린샷 등 추가 자료는 릴리즈에 첨부할 수 있지만 앱용 체크섬 파일에는 포함하지 않습니다.

1. 최종 후보의 필수 결과와 소스·APK 대응을 확인합니다.
2. 허용한 공개 파일 목록을 정합니다. 초기에는 APK·체크섬면 충분합니다.
3. 기존 공개 버전과 충돌하지 않는 버전·태그를 확인합니다.
4. 준비한 파일을 초안 릴리즈에 올립니다.
5. 원격의 파일명·크기·해시와 재다운로드 바이트를 비교합니다.
6. 검증 후 공개하고 공개 URL에서도 내려받아 확인합니다.

재시도할 때 같은 파일은 보존하고 빠진 파일만 추가합니다. 같은 이름의 다른 바이트, 예상하지 못한 첨부 파일, 도중 바뀐 태그는 충돌로 다룹니다. 파일을 올리는 코드와 앱의 필수 검사·서명 검증을 강제하는 코드는 서로 다른 책임입니다.

향후 게시 도구를 구현하면 검증 manifest와 APK 해시를 연결하여 다른 후보가 올라가지 않게 합니다. 존재하지 않는 통합 명령이나 자동 차단 기능이 이미 있다고 문서화하지 않습니다. workflow의 동시 실행 제한이 다른 컴퓨터의 로컬 실행까지 잠그는 것도 아닙니다.

## 6. 릴리즈 검증 기록 템플릿

아래 표를 버전별 문서에 복사하고 `미실행`부터 작성합니다.

| 항목 | 결과 | 근거 |
| --- | --- | --- |
| 소스·APK·버전·서명 | 미실행 | 커밋·해시·검증 로그 |
| TXT 정확성·저장소·이전 | 미실행 | fixture·실제 테스트 목록·결과 |
| UI·큰 글씨·접근성 | 미실행 | 기기·글자 배율·캡처·결과 |
| 프로세스 종료 후 복원 | 미실행 | 이전/새 PID·문자 앵커 |
| 스크롤·열기·메모리 | 미실행 | 조건·P50/P95/P99·트레이스 |
| 신규 설치·덮어 설치 | 미실행 | 앱 ID·원본/기록/설정 비교 |
| 실제 SAF·시작 흐름 | 미실행 | 시작 폴더·재부팅·이어 읽기 확인·권한 상실 |
| 공개 파일 재다운로드 | 미실행 | 로컬/공개 해시·바이트 |
| 미검증 범위 | 미기록 | OS·제조사·기능·제외 이유 |

필수 검증 완료와 공개 파일 확인 완료를 구분하여 기록합니다. 구체적인 성능·동작 기준은 [검증 계획](e2e.md)을 따릅니다.


## 작업 종료 후 정리

[문서와 산출물 정리 규칙](development.md#문서와-산출물-정리)에 따라 버전별 결과 두 문서를 Git에 남기고 일회성 자료를 삭제합니다.

작업 파일은 `.tools/verification/<실행 ID>/`, 고정 APK는 `.tools/releases/<버전>/`을 사용합니다. 기존 `.tools/signing/`과 `signing.properties`를 유지하며 공개 APK의 인증서와 일치하는 키를 사용합니다.
